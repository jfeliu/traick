System Architecture

Traick: from one WhatsApp message to a tracked project

Traick is a single FastAPI process. A Meta webhook drops each inbound message into SQLite, a local Ollama model writes the reply, and three interval jobs turn the backlog into projects, action items, and follow-up reminders.

01The whole system

One process serves the webhook, runs the scheduler, and hosts the admin UI. Everything shares traick.db. The only outbound dependencies are the Meta Cloud API and a local Ollama server.

in-process call / HTTP request automatic reply (within 24 h window) SQLite read / write APScheduler interval job

02Lifecycle of one inbound message

Two independent timelines start from a single POST /webhook.

  1. Meta delivers the message.

    The payload is validated; senders outside ALLOWED_NUMBERS and non-text types are dropped. The row is saved to raw_messages with processed = 0.

  2. A BackgroundTask writes the reply.

    _handle_reply loads the sender's active projects and last 10 messages, asks Ollama for a reply, and — unless the model returns NO_REPLY or repeats the last outgoing line — sends it via send_message.

  3. Every 5 min: extraction.

    process_pending_messages pulls up to BATCH_SIZE unprocessed rows, groups them by sender, and per group calls extract_from_messages. Instructor forces the model output into ExtractionResult; projects are upserted by (owner_number, name), action items and any suggested follow-up are inserted, then the rows are marked processed = 1.

  4. Every 15 min: reminders.

    send_due_reminders finds follow-ups with scheduled_at ≤ now and sent = 0, sends each through the approved traick_recordatori_v2 template (works outside the 24 h window), and marks them sent = 1.

  5. Every 24 h: safety net.

    ensure_active_project_followups finds active projects with no pending follow-up and generates one, so nothing the extractor missed goes silent.

03Data model

Four tables in traick.db, created on startup by init_db(). Projects are scoped per contact — there is no user table; owner_number is the tenant key.

04Scheduled jobs

JobCadenceReadsWritesExternal call
process_pending_messages every 5 min raw_messages where processed = 0, existing projects projects, action_items, follow_ups; marks messages processed Ollama — extract_from_messages (JSON / Instructor)
send_due_reminders every 15 min follow_ups due and unsent, joined to projects follow_ups.sent = 1 Meta — send_template_message (traick_recordatori_v2)
ensure_active_project_followups every 24 h active projects with no pending follow_up follow_ups Ollama — generate_follow_up_for_project

All three run in-process on AsyncIOScheduler, started and stopped by the FastAPI lifespan handler. Intervals for the first two are configurable via PROCESS_INTERVAL_MINUTES and REMINDER_INTERVAL_MINUTES.

05Stack & boundaries

  • FastAPI + UvicornWebhook, admin, dev routers; one process, one port.
  • APSchedulerIn-process interval jobs, no separate worker or broker.
  • SQLite via aiosqliteSingle file traick.db; schema built on startup.
  • OllamaLocal model over the OpenAI-compatible API; never leaves the host.
  • Instructor + PydanticValidated structured output for extraction.
  • Meta WhatsApp Cloud APIInbound webhook; outbound free-form and template sends.
  • Jinja2Server-rendered admin UI under /admin/*, session-cookie auth.
  • Starlette SessionMiddlewarePlus a host-rewrite shim mapping an admin subdomain to /admin.
